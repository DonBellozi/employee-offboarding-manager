# Сопоставление AD у уже уволенного работника

Основа: GitHub HEAD `681c1f94dee99c14b7d3566b6a6d005647c6f8cf`, скачанный
отдельно. Исходные версии трёх изменяемых файлов совпали с HEAD (CRLF/LF
нормализованы). Локальные изменения сохранены, GitHub не изменялся.

## Установленная причина

В задаче #101 за 06.11.2026 у одного worker_key остаются две исторические
записи с логинами kotlyarenko.av и kotliarenko.av, обе is_present=0.
EmailLoginMapping отсутствует. Поэтому прежний ремонт ad:conflict не может
считать план исправленным: кадровые логины всё ещё неоднозначны.
Карточка подробностей показывает AD из одной предпочитаемой записи, что
не заменяет подтверждение общей идентичности для двух организаций.

Общая форма кадрового сопоставления допускает только текущие is_present=1
записи. Новая форма решает исторический случай отдельно, не ослабляя эту защиту.

## Что добавлено

- У администратора в строке ближайшего увольнения с открытой ad:conflict
  появляется «Сопоставить AD».
- GET/POST `/dismissals/{run_id}/ad-mapping`, существующий router уже
  подключён приложением. Схема БД и зависимости не меняются.
- Сначала ввод точного логина и проверка AD. Показываются ФИО, статус,
  objectGUID. Затем отдельное подтверждение, по умолчанию не отмеченное.
- При сохранении заново читается AD и сравнивается objectGUID с проверенным.
  ФИО должно совпасть с кадровой историей (регистр, пробелы, ё/е нормализуются).
  Чужое сопоставление того же GUID запрещает сохранение.
- Кадровое состояние проверяется до и после чтения AD: выполняющийся импорт,
  активная занятость хоть в одной организации, другой эпизод увольнения,
  завершённая/отменённая задача или отсутствие ad:conflict блокируют действие.
- Одна подтверждённая AD сохраняется через существующие EmailLoginMapping
  для всех перечисленных исторических источников этого worker_key.
  Предыдущие AD-сопоставления показаны оператору и сохраняются в аудите изменений.
- HRSourceRecord.login/is_present не меняются; Zimbra ID, адреса и текущие
  почтовые сопоставления сохраняются. Новых учёток и паролей не создаётся.
- Действие только читает AD и сохраняет связи в локальной БД. Не включает,
  не выключает, не удаляет AD, не обращается к Zimbra. Нет массовой сверки
  всех работников после сохранения. Результат увольнения не выставляется
  «успешным» только на основании ручного выбора.
- GET и POST требуют роль admin, POST — CSRF. Неизвестные действия отклоняются;
  ошибки соединения AD не раскрывают технические секреты.

## Для задачи #101

После установки и пересборки контейнера:

1. Войти с ролью «Администратор».
2. У Котляренко открыть «Сопоставить AD». Прямой путь на вашем сервере:
   `/dismissals/101/ad-mapping`.
3. Ввести `kotlyarenko.av`, нажать «Проверить AD».
4. Убедиться, что показаны нужный работник и учётка, отметить подтверждение,
   нажать «Сохранить сопоставление».

Это пользовательский выбор для конкретного случая, не захардкоженное имя в коде.
Автоматика затем выполнит штатные проверки. Уже выключенная учётка будет
подтверждена без повторной команды блокировки. Увольнение перейдёт в журнал
в той же записи, а старая диагностика сохранится как устранённая.

Сохранение НЕ запускает блокировку немедленно и не обходит контрольные выгрузки,
импорт, срок увольнения или отсрочку. Если ещё нет контрольных выгрузок текущего
дня, задача ждёт их по существующим правилам; до этого в кэше подробностей может
оставаться прежний статус. Если AD недоступна/ФИО не совпадает, ошибка не скрывается.

## Проверки и установка

74 профильных pytest, включая 13 новых сценариев. Воспроизведены два разных
логина в отсутствующих кадровых строках → предварительная проверка без записи →
подтверждение GUID → сохранение обеих связей без правки HR → успешное завершение
того же run и исчезновение из ближайших. Проверены чужой GUID, смена GUID,
активная другая организация, импорт во время LDAP-запроса, повторное сохранение,
сохранность Zimbra-связей, права/CSRF и ошибки AD. Реальная AD подменена в тестах.
Проверены py_compile, Jinja-рендер формы/фрагмента, вид новой страницы в браузере.
JavaScript не изменялся. Тест использует существующий fixture test_ad_conflict_recovery
из предыдущего исправления, присутствующий в указанном HEAD.

7 файлов: 3 изменённых, 4 новых. Удалений нет. Перед применением сохранить
копию исходников и резервную копию БД. Распаковать repo-relative пути поверх
исходников, пересобрать существующий Docker-сервис и пересоздать контейнер,
сохранив окружение, compose-проект и тома. Одного restart недостаточно.
Не удалять том БД. Автоматического развёртывания и изменений производственных
учёток не выполнялось. ZIP integrity и SHA-256 проверены перед передачей.
