# Устранённая коллизия AD удерживает увольнение в ближайших

Основа: GitHub HEAD `9ca1a85456df20c679a76e857dc6b212b427eb43`, скачанный
отдельно 09.11.2026. Исходный сервис побайтно по тексту после нормализации
CRLF/LF совпал с HEAD. Локальные наработки не перезаписывались, GitHub не изменён.

## Причина

Неоднозначность логина, сопоставления или GUID создаёт диагностическую цель
`ad:conflict` в состоянии `intervention`. После исправления данных планировщик
добавлял корректную цель AD, но сохранял старую открытую ошибку. Даже после
успешной блокировки корректной цели итог оставался `partial`, без completed_at.
Список ближайших правильно ждал завершения, а журнал не получал объект.

## Исправление

- Если новый кадровый план определяет одну корректную цель AD без ошибки,
  устаревшая диагностическая цель помечается отменённой с результатом
  `ad_conflict_resolved`. Это не отметка «УЗ заблокирована».
- Диагностика с исходным текстом остаётся в БД, добавляется аудит устранения
  коллизии. Повторная обработка не дублирует аудит для той же отменённой цели.
- Только эта отменённая диагностика исключается из вычисления результата.
  Реальные ошибки AD, другие отмены и прочие цели не скрываются.
- Корректная цель проходит обычную обработку. Если учётка уже выключена,
  фиксируется `already_completed`, без повторной команды блокировки.
- Уже завершённые корректные цели не выполняются повторно. Это исправляет и
  ранее застрявшие записи, где корректная цель уже успела завершиться.
- Если неоднозначность появляется снова до завершения, диагностическая цель
  снова становится `intervention`. Перед AD-действием текущий план проверяется
  ещё раз, чтобы старая ожидающая цель не обошла новую коллизию. Заблокированная
  по этой причине цель повторно ставится в pending только после устранения
  коллизии в её текущем плане; ошибки доступа/сети так не сбрасываются.
- Если план вообще исчез, старая коллизия не считается устранённой автоматически.

Успешное увольнение сразу уходит из «Ближайших» в существующий единый журнал.
Ни второй эпизод увольнения, ни новая строка журнала не создаются.
Zimbra, DSM и Техэксперт не объединяются с AD в одну политику.

## Применение

Архив: один изменённый сервис, новый файл тестов и эта инструкция.
Удалений, изменений схемы БД, зависимостей, Jinja или JS нет.

Сохранить текущие файлы и резервную копию БД, распаковать архив с сохранением
repo-relative путей, пересобрать существующий Docker-сервис и пересоздать
контейнер, сохранив compose-проект, настройки и тома. Не удалять БД/тома.
Одного restart при COPY исходников в образ недостаточно.

Старые записи подхватит штатный минутный цикл, когда выполнены обычные условия:
готовы контрольные кадровые выгрузки всех источников, не идёт импорт, наступил
срок действия с учётом отсрочки и нигде нет активной занятости. Исправление
не обходит эти проверки и не обещает безусловный перенос по таймеру.
Если реальная AD-проверка вернёт ошибку, запись обоснованно останется в ближайших.
Реальное развёртывание и изменения производственных учёток не выполнялись.

## Проверки

84 профильных pytest, включая 9 новых сценариев на реальной тестовой SQLite
с подменой только внешней AD и готовности источников:

- исходная коллизия → исправление → уже выключенная AD → один объект журнала;
- старый корректный target уже завершён, идемпотентная повторная обработка;
- неустранённая/повторная коллизия и исчезнувший план;
- реальная ошибка AD остаётся ошибкой;
- неготовые источники, отсрочка, активная занятость во второй организации.

Проверены также существующие тесты ближайших, журнала, кадровых защит,
точечной сверки и кэша подробностей; py_compile сервиса и теста.
ZIP проверен на целостность, дубли/пути и совпадение содержимого с исходниками;
SHA-256 предоставлен вместе с архивом.
