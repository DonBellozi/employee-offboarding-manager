# Компактная форма и проверка владельца занятого логина — первая часть

(05.11.2026). Копия HEAD скачана отдельно: локальное дерево с предыдущими

## Что включено

- Две колонки в форме: логин/домен/повторная проверка слева,
  независимые статусы AD/Zimbra и создание справа. На узком экране — одна колонка.
- Короткое описание, одна строка предупреждения вместо двух повторяющихся.
- Памятка журнала: **Пароли не сохраняются в журнале.** Они доступны только
  на итоговом экране и в отправленных письмах.
- Отдельный авторизованный GET `/employees/login-owner?login=...` без записи
  в базу или внешние системы; ответ `Cache-Control: no-store`.
- Проверка владельца выполняется только при занятом выбранном логине,
  не при пакетном переборе альтернатив. Смена ввода отменяет старый запрос,
  устаревшие ответы не показываются. Все внешние строки выводятся как текст,
  без HTML-интерпретации. Ошибки соединения не раскрывают ответ сервера/секреты.
- Используются фактические GUID AD / ID Zimbra, существующие сопоставления,
  точные корпоративные адреса и кадровое состояние по всем организациям.
  Совпадение сгенерированного логина или одного ФИО не является доказательством.
- Несколько владельцев, противоречие ID и адреса, незавершённый кадровый импорт
  и конфликт с созданием до оформления требуют проверки. Новые УЗ с закреплённым
  ID в механизме предварительного создания показываются как ожидающие кадров.
- AD и почта оцениваются отдельно, в том числе если у них разные владельцы.

Это информационная проверка по последним загруженным кадровым данным, а не
разрешение на удаление. Отсутствие активной занятости не приравнивается
к подтверждённому увольнению. Свежесть/полнота импорта и повторная проверка
непосредственно перед действием потребуются в механизме пересоздания.
Штатная серверная защита создания занятого логина сохранена.

## Что НЕ включено в этот архив

Фоновое пересоздание, ранняя выдача закреплённых паролей, новые состояния
журнала «Подготовка» / Zimbra «Создается» и запись в Synology ещё не реализованы.
Не добавлялась неработающая кнопка пересоздания с опасной заглушкой.

Согласовано для следующего этапа:

1. Одна сохраняемая задача, неизменные утверждённые реквизиты, секреты
   зашифрованы, восстановление после перезапуска без повторного удаления.
2. Перед каждым разрушительным действием — проверка точного владельца и
   неизменности GUID/ID, полной актуальной занятости во всех организациях,
   блокировок/отсрочек и конфликтов с другими задачами.
3. Новый AD создаётся первым, старый ящик не должен стать доступен новому
   владельцу через AD-аутентификацию. AD новой учётки имеет новую идентичность:
   нельзя молча перенести прежние сопоставления и права.
4. Почта сохраняется в архив, архив проверяется; новый ящик ПУСТОЙ.
   Перенос старых писем новому сотруднику запрещён. Имеющаяся проверка
   ненулевого размера TGZ недостаточна как проверка восстановимости.
5. «Успешно» только после проверки всех запрошенных УЗ. При частичной ошибке
   продолжать с нужного шага, не пересоздавать уже готовую AD повторно.
6. Synology: только добавление готового блока копирования в конец документа,
   между блоками ровно два пробела. Существующий текст не менять.
   Сохраняемая зашифрованная очередь повторяет ошибки/неопределённый результат;
   возможный дубль предпочтительнее потери данных. Подтверждение записи
   обязательно, одного успешного HTTP-ответа недостаточно.

## Synology: проведённая диагностика

Получены адреса рабочего и тестового документов, заявлена версия Office
4.0.4-27894. NAS доступен. Выполнены только чтение стартовой страницы и
запросы метаданных API; рабочий и тестовый документы не изменялись, содержимое
с паролями не извлекалось. API.Info перечисляет Office API; запрос Office.Info
без авторизованной сессии вернул `success:false`, код 119. Наличие API в каталоге
не подтверждает поддержку безопасного append в совместно редактируемый документ.

Для продолжения нужны служебный доступ с правами на тестовый документ,
защищённое подключение (HTTPS с проверкой сертификата либо защищённый туннель)
и проверка поддерживаемого способа добавления с учётом одновременных правок.
Нельзя подменять append скачиванием/перезаписью всего документа или напрямую
редактировать внутренние файлы Office. Пароли не передавать в чат.

Публичный обзор API: https://www.synology.com/en-global/dsm/feature/productivityapi
Он описывает append ячеек Spreadsheet, но не подтверждает append текста Document;
документация полного API предоставляется через Synology Account.
