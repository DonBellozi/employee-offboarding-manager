# Решения о необходимости корпоративной учетной записи — этап 1

## Что изменилось

Случай решения привязан к существующему `HREmploymentArrivalEvent`, а не только к человеку.
Связь с человеком — прежний HMAC `worker_key`; алгоритм идентификации не меняется.
Одновременные появления одного человека в нескольких организациях объединяются через
`account_requirement_arrivals` в один случай. Снимок включает все активные размещения,
включая занятость с предстоящей датой увольнения. При повторном приеме возникает новый случай.

Отдельный фоновый поток раз в минуту проверяет новые появления через существующий
`EmployeeArrivalAccountService.inspect`. До 10 человек за проход, повторная проверка
того же человека не чаще пяти минут, с приоритетом еще не проверенных. Открытие
карточки также выполняет проверку. Поток не создает/восстанавливает учетки и не отправляет письма.
При выполняющемся кадровом импорте сбор и принятие решений ожидают его завершения.

Если AD/Zimbra не удалось проверить либо проверка отключена, отсутствие учеток не считается
доказанным и новый случай не размечается. Найденные учетки, включая отключенные,
остаются в существующем сценарии сопоставления/восстановления. Поиск учитывает
активные кадровые записи человека во всех организациях.

В карточке нового работника:

- **Учетная запись нужна** — сначала сохраняет решение и снимок, затем открывает
  прежнюю форму создания с выбором логина/домена. Само внешнее создание выполняется
  прежней кнопкой формы, не фоновым процессом.
- **Требуется уточнение** — сохраняет промежуточное состояние без обучающей метки.
- **Учетная запись не нужна** — требует отдельной отметки подтверждения, закрывает
  соответствующие уведомления о новом работнике, не выполняет внешних действий.

Быстрая старая кнопка «Не требуется» на главной убрана, чтобы не записывать отрицательные
решения до проверки существующих учеток. Старый POST-адрес только открывает карточку
решения после проверки и больше не принимает отрицательный ответ напрямую.

## Хранение и история

Добавляются три таблицы: `account_requirement_cases`,
`account_requirement_arrivals`, `account_requirement_decision_events`.
Новые таблицы создаются существующим `Base.metadata.create_all` при запуске;
существующие таблицы/данные не пересоздаются и не удаляются.

`initial_snapshot_json` фиксируется при создании случая.
`decision_snapshot_json` фиксируется при первом финальном ответе.
При исправлении ответа кадровый снимок остается прежним: исправляется метка для того
же кадрового состояния. История хранит предыдущие/новые состояния и ответы,
оператора, время, комментарий, копию снимка и SHA-256.
Текущая метка находится в случае; история — добавляемые записи, без удаления.
В общем аудите сохраняются ID случая, переход, решение и хеш, без ФИО/кадрового JSON.

Уточнение сохраняется как постоянный флаг, а окончательный источник —
`manager_clarification` либо `operator`. Будущие поля модели пока NULL.
Реестр моделей, обучение и рекомендательная шкала относятся к следующему этапу,
в этом обновлении их нет.

Исправлять свой финальный ответ может оператор, чужой — администратор.
Старая открытая форма не может перезаписать более новое решение: проверяется revision,
дополнительно используется optimistic locking SQLAlchemy.
Администратор может отменить ошибочный случай с указанием причины; история остается,
случай исключается из экспорта. Отмена/исправление ответа не удаляют созданные учетки
и не отменяют уже начатые внешние действия.

Незавершенные случаи автоматически отменяются, когда соответствующие появления
завершились либо приняты существующие учетки. Сопоставление/восстановление существующих
учеток отменяет связанный случай и не превращает его в `not_required`.
Успешное создание новых учеток через связанное решение сохраняет положительную метку.
Технический результат создания хранится отдельно, ошибка не меняет решение `required`.

Старые отрицательные решения из общего аудита не импортируются автоматически:
для них нельзя достоверно восстановить исходный кадровый снимок и исключить reuse.

## Административный список и экспорт

Ссылка **Решения об УЗ** в шапке доступна роли администратора.
Адрес: `/admin/account-requirements`. Есть фильтры состояния, решения, периода,
организации, подразделения, должности. Из списка открывается история и исправление.

JSON: `/admin/account-requirements-export`.
Выгружаются все действующие финальные случаи, независимо от фильтров списка.
`build_account_requirement_dataset(db)` формирует:

- `X`: организация, подразделение, должность, полный список размещений и их количество;
- `y`: 1 = нужна, 0 = не нужна;
- технические метаданные: ID случая, версия схемы снимка, SHA-256 снимка;
- версия схемы датасета, количество записей и `dataset_sha256`.

В `X` и выгрузке нет ФИО, worker_key, СНИЛС, адресов, логинов, паролей, GUID,
комментариев, результатов создания или флага уточнения. Экспорт строится по
неизменяемому снимку, а не по текущей кадровой карточке. `dataset_sha256` считается
по UTF-8 JSON без самого поля хеша, с `ensure_ascii=False`, `sort_keys=True`,
`separators=(',', ':')`. Одинаковое содержимое дает одинаковый хеш.

## Обновление Docker / Portainer

Архив содержит только измененные и новые файлы с путями от корня репозитория.
Удалений нет. Перед обновлением сохраните резервную копию исходников и постоянной БД.
Накладывать на текущую рабочую версию проекта, не на чистый старый HEAD:
обновление использует уже установленные доработки employee_arrivals.

В вашей инфраструктуре контейнер приложения — `employee-offboarding-manager`,
существующий Compose project — `account_provisioner_mvp`, хост Docker — Linux.
Исходники Portainer ранее были по адресу:
`/var/lib/docker/volumes/portainer_data/_data/compose/22/7bb19a69a08ad0d39e6a32f2767312e2da2acacb`.
Путь может измениться при новом git-развертывании — сначала проверьте актуальный путь.

После наложения файлов нужен **rebuild/redeploy существующего стека**, поскольку
приложение копируется в Docker image. Простой restart не подхватит измененные файлы хоста.
Сохраните текущие имя проекта, переменные stack.env и постоянные тома.
Не выполнять down с удалением томов и не менять Compose project при обновлении.
Если стек управляется git в Portainer, ручные изменения служебного checkout могут быть
перезаписаны последующим развертыванием — сохраните патч отдельно.

Проверка после запуска: открыть нового работника без учеток, выбрать «Уточнение»,
затем «Нужна»; убедиться, что открылась старая форма создания и случай виден в
административном списке. Для второго тестового случая выбрать «Не нужна» с подтверждением.
JSON должен содержать только финальные ответы. Реальные AD/SMTP действия в автоматических
тестах заменены заглушками; проверка против вашей инфраструктуры остается за оператором.

## Проверки патча

Расширенный прогон Python: 732 теста прошли, 9 не прошли. Те же 9 ошибок
воспроизведены отдельно на сохраненной версии исходников до этого патча:
8 в `test_worker_identity.py`, 1 в `test_zimbra_protection.py`.
Эти исходники/тесты не изменялись данным обновлением.
Тесты, глобально подменяющие модули AD/Zimbra, запускались в отдельных процессах,
чтобы их заглушки не влияли на остальные проверки.

Целевые проверки: решения/история/JSON, новые работники, кадровый реестр,
стабильные сопоставления, журнал и увольнения. Дополнительно проверяются
`py_compile`, измененные Jinja-шаблоны и синтаксис JavaScript отрендеренной формы.
Проверки внешних сервисов выполняются без реальных действий в AD/Zimbra/SMTP.
