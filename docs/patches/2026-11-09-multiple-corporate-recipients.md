## Область применения

Доработано полное создание УЗ с объединённым письмом, а также его частичный
результат (только готовые реквизиты почты, если AD не включилась).
Отдельное досоздание только AD/только почты, пересоздание и восстановление
не менялись. Новых команд блокировки/восстановления или правил увольнения нет.

## Определение получателей

- При создании из кадрового уведомления сервер передаёт ID выбранных событий,
  не произвольный worker_key из формы. Сервис проверяет регистрацию до создания
  УЗ и снова непосредственно перед планированием писем. Сопоставление должно
  сохранять worker_key и ФИО (без учёта регистра, пробелов, ё/е).
- Используются корпоративные адреса всех текущих HRSourceRecord одного
  worker_key с активной/запланированной занятостью в соответствующем источнике
  и is_present=True. Исторические/исчезнувшие строки не добавляются.
- Создаваемая почта и явно указанный личный адрес остаются получателями.
  При ручном создании без кадрового уведомления не угадываем человека по ФИО
  или сгенерированному логину: дополнительных кадровых адресов не добавляем.
- Импорт в процессе, изменившееся кадровое сопоставление или противоречивый
  владелец дополнительного адреса останавливают именно расширение списка
  адресов с предупреждением. Уже созданные УЗ не откатываются.
- Дополнительные ящики проверяются одним пакетным чтением Zimbra по точным
  адресам. Нужны ID ящика, подтверждённый адрес в его адресах и статус active.
  Противоречие с другим worker_key по адресу или zimbraId запрещает отправку.
  Закрытый ящик пропускается; неподтверждённый вызывает предупреждение.
- Адреса разных самостоятельных ящиков получают отдельные экземпляры письма.
  Алиасы одного zimbraId получают один экземпляр на выбранный текущий адрес.
  Известные алиасы только что созданного ящика также объединяются без повтора.
  Подтверждённое совпадение личного адреса с корпоративным обрабатывается
  аналогично. Неподтверждённые совпадения по локальной части адреса не угадываются.

Содержимое у всех экземпляров одинаковое: новые реквизиты текущей операции.
Пароли существующих дополнительных ящиков не извлекаются и не сбрасываются.
Получатели не объединяются в To/Cc/Bcc.

## Учёт доставки

Добавлена таблица `credential_deliveries`: операция, исходный адрес,
фактический адрес отправки, статус, безопасное пояснение и время отправки.
Уникальность — операция + адрес. В таблице нет паролей, HTML письма и секретов.
Она автоматически создаётся штатным Base.metadata.create_all при запуске;
существующие таблицы не пересоздаются. Новых зависимостей нет.

Для алиасов сохраняются отдельные строки с одним фактическим получателем.
Успешность группы обновляется вместе. На итоговом экране и в подробностях
журнала выводится отдельная строка каждого адреса: отправлено, не отправлено,
пропущено, требует проверки, ожидает отправки. Старые записи без этой таблицы
продолжают использовать прежние флаги; история задним числом не переписывается.
Прежние personal_mail_sent/corporate_mail_sent поддерживаются для совместимости.

SMTP повторяет попытки для проблемного физического получателя в рамках
существующих настроек SMTP_RETRY_ATTEMPTS/SMTP_RETRY_DELAY_SECONDS, не вызывая
повторно отправку для успешно обслуженной группы. После исчерпания попыток
результат остаётся failed и операция partial. Успешность дополнительных адресов
тоже учитывается в результате операции; закрытый необязательный ящик — skipped.

Это не сохраняемая очередь с паролями. При прерывании процесса pending остаётся
метаданными, автоматическая повторная отправка после перезапуска не обещается:
пароли не сохраняются. SMTP exactly-once при неопределённом принятии DATA
не гарантируется. Успешный статус означает принятие SMTP, не прочтение письма.

## Проверки

190 профильных pytest, в том числе 20 новых сценариев; отдельно 12 тестов
досоздания AD (их глобальные заглушки требуют изоляции). Проверены:

- регистрация через веб-маршрут с серверным кадровым контекстом;
- несколько текущих организаций, исторические/исчезнувшие строки;
- несколько отдельных ящиков, общий zimbraId, одинаковые адреса, личный=алиас;
- закрытый/неподтверждённый ящик, ошибка подключения, чужое сопоставление;
- отдельные SMTP-повторы и сохранение результата каждого адреса;
- изменение ФИО в форме, невалидные события, выполняющийся импорт;
- сохранность старых записей и отсутствие секретов в метаданных/журнале;
- прежние объединённые письма, решения об УЗ и кадровые уведомления;
- py_compile, Jinja-рендер, JS формы и итоговой страницы;
- браузерные desktop/mobile проверки трёх адресов без горизонтального переполнения.

Реальные AD, Zimbra и SMTP в тестах подменены, производственная рассылка
не запускалась. ZIP проверен на целостность и совпадение с исходниками.

## Установка

10 файлов: 7 изменённых и 3 новых. Удалений нет.
Сохранить резервную копию БД и текущих файлов. Распаковать с repo-relative
путями, пересобрать существующий Docker-сервис и пересоздать контейнер,
сохранив compose-проект, окружение и тома. Не удалять том с БД.
Простого restart для образа с COPY исходников недостаточно.
Развёртывание автоматически не выполнялось.
