# «Учетная запись нужна»: исправление Not Found

Основа: проверенный HEAD `a81e64c489a1210f721c65ff2af40294a5277b7e`.
Рабочая копия PyCharm совпадала с этим коммитом, незаписанных изменений не было.

## Причина

Форма нового работника отправляет POST на
`/employees/account-requirements/{case_id}/decision`.
Обработчик существует в `app/routers/account_requirement.py`, но этот роутер
не был подключён в `app/main.py`. Поэтому сервер возвращал стандартное
`{"detail":"Not Found"}` ещё до обработки решения.

В текущем `main.py` также отсутствовал запуск существующего
`AccountRequirementWorker`, обслуживающего фоновый сбор решений и привязку
созданных до выгрузки учётных записей.

## Изменения

- Подключён существующий роутер решений об УЗ, включая историю и раздел администратора.
- Восстановлены создание, запуск и остановка существующего фонового обработчика
  решений вместе с приложением. Он выполняет обнаружение, а не создание/восстановление учёток.
- Правила принятия решения, повторной проверки HR/AD/Zimbra, права доступа и CSRF
  не менялись. При выборе «Нужна» решение сохраняется, а оператор переходит к
  заполненной форме проверки и создания УЗ. Создание требует отдельного действия.
- Предыдущая доработка индикатора оборудования сохраняется: её файлы не заменяются.

Новых зависимостей и изменений схемы БД нет.

## Проверки

Регрессионный тест на настоящем `app.main.app` до исправления подтвердил
отсутствие маршрута в приложении. Прежние тесты отдельно собирали тестовый
FastAPI с обоими роутерами и поэтому такую ошибку подключения не обнаруживали.

После исправления:

```text
pytest tests/test_account_requirement_wiring.py tests/test_upcoming_equipment_indicator.py tests/test_dismissal_details_cache.py -q
59 passed
```

Проверены регистрация маршрутов в настоящем приложении, решение и переход к
заполненной форме, отсутствие создания УЗ при принятии решения, сохранение
истории без дублирования при обновлении формы, ошибки каталога, существующая
учётка, устаревшая версия решения, незавершённый импорт, CSRF и роль оператора.
Отдельно проверены запуск/остановка фонового обработчика при нормальном выходе
и исключении внутри контекста приложения.

Тесты используют БД в памяти и подменённые внешние проверки. Зарегистрированные
обработчики и Jinja-шаблоны вызываются без HTTP-сокетов; рабочие AD/Zimbra/SMTP
не задействованы. Выполнены py_compile и разбор Jinja. Шаблоны/JS не изменялись.
Проверены состав ZIP, целостность, относительные пути, совпадение байтов и SHA-256.

## Установка через PyCharm и Portainer

1. Распаковать ZIP поверх `D:\Python\employee-account-manager`, сохранив пути.
2. В PyCharm выполнить Commit и Push исправления в ветку, которую читает Portainer.
3. В Portainer обновить стек через Pull and redeploy.

Убедиться, что контейнер использует образ с обновлённым `app/main.py`.
Повторить действие для уже найденного работника; создавать новую кадровую
запись или удалять существующее решение не требуется.

При необходимости наличие маршрута в файлах образа проверяется на Docker-сервере:

```bash
sudo docker exec employee-offboarding-manager python -c "from app.main import app; print('/employees/account-requirements/{case_id}/decision' in app.openapi()['paths'])"
```

Ожидается `True`. Эта проверка не запускает lifespan и фоновые потоки приложения.

В ZIP три файла: изменённый `app/main.py`, новый тест и эта памятка.
Удалений нет. Изменения в GitHub не отправлялись.
