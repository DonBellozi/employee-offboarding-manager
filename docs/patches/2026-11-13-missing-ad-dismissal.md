# Отсутствующая AD-учётка не удерживает увольнение

Основа: актуальный GitHub HEAD `005c2023f29990473f24fcc6cfcb4bf8de2adb26`.
Оба изменяемых исходника совпали с ним до правок после нормализации CRLF/LF.
GitHub и производственные системы не изменялись.

## Причина и новое поведение

В кадровых данных может быть указан планируемый логин, хотя учётку работнику
не создавали. Раньше пустой результат поиска переводил AD-цель в постоянное
состояние intervention с ошибкой «Учетная запись AD не найдена». Такая цель
не повторялась и удерживала увольнение в «Ближайших увольнениях».

Теперь после пустого поиска логина система отдельно подтверждает его
отсутствие по всему домену AD. Она читает корень домена из RootDSE, сверяет
его с настроенным доменом и выполняет точный поиск sAMAccountName во всём
поддереве. Пустой ответ при успешном полном поиске завершает цель как
already_completed / confirmed_absent. В журнале показывается «Отсутствует»,
а не «Заблокирован». При завершении остальных этапов запись сразу переходит
в журнал обычным механизмом, без дубликата.

Отключённая проверка AD, пустой логин, другой/неопределённый домен, ограничение
результатов, перенаправления и ошибки прав не считаются отсутствием.
Временная недоступность AD, таймаут или ответ busy/unavailable оставляют
цель на повторную попытку с существующим интервалом повторов.

## Уже зависшие записи

Автоматически подхватываются только прежние AD-цели intervention с точной
ошибкой «Учетная запись AD не найдена», известным логином и без сохранённого
objectGUID, при однозначном актуальном плане. Проверка таких целей выполняет
только чтение AD. Если учётка теперь найдена, требуется подтвердить
сопоставление; автоматической блокировки в рамках исправления нет.

Режим проверки без блокировки сохраняется после сетевых повторов и
промежуточного конфликта кадровых логинов. Остальные intervention не
перезапускаются этим исправлением. Прежний механизм проверки удалённого
объекта по известному GUID сохранён; он не заменён поиском только по логину.

Сохраняются проверки свежести кадровых источников, выполняющегося импорта,
активной занятости во всех организациях, даты включения автоматики и срока
с учётом общей отсрочки. Перед обработкой повторно проверяется кадровое
состояние. Поэтому устранение зависания начнётся в очередном фоновом цикле,
когда эти условия выполнены и AD доступна.

Подтверждённо отсутствующая учётка также не создаёт предупреждение о
восстановлении AD при последующем возвращении работника: восстанавливать
такую учётку нечего. Сценарии новых работников и сопоставления остаются прежними.

Изменён только контур AD. Почта, DSM, Техэксперт и их организационные правила
не менялись. IT Invent остаётся read-only; 1С Бухгалтерия и 1С ДО не добавлялись.

## Проверки и установка

- 140 профильных pytest: LDAP-подтверждение, перенос в журнал, старое
  зависание, сетевые повторы, обнаруженная учётка, конфликт, отсрочка,
  другая активная организация, импорт, свежесть данных, известный GUID,
  сопоставления и существующие проверки увольнений.
- py_compile обоих изменённых модулей и нового теста.
- Jinja и JavaScript не затронуты. Отображение отсутствующей AD в журнале
  проверено через существующий сборщик данных журнала.
- Внешние AD/Zimbra и производственная БД в тестах не использовались.

ZIP содержит два изменённых модуля, новый тест и эту памятку, с путями
от корня репозитория. Удалений нет. Новый тест использует существующий
test_ad_conflict_recovery из указанного HEAD. Зависимости и схема БД прежние.
Целостность ZIP и SHA-256 проверяются при сборке архива.

Распаковать в корень проекта с заменой файлов, пересобрать и пересоздать
существующий контейнер приложения. Одного restart недостаточно, если
исходники копируются в образ при сборке. Автоматическое развёртывание
не выполнялось.
