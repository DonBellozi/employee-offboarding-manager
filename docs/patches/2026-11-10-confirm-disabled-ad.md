# Явное подтверждение уже заблокированной AD

Основа: GitHub HEAD `fc134450cbc54ad521e1ca6cea43ad6ffa9c183a`, скачанный
отдельно. Исходные версии трёх изменяемых файлов сверены с HEAD после
нормализации CRLF/LF. Локальное дерево не сбрасывалось, GitHub не изменялся.

## Зачем

После сохранения исторического AD-сопоставления раньше оставалось только ждать
фонового обработчика. Он прежде всего проверяет готовность контрольных
кадровых выгрузок текущего дня; отказ этой проверки не записывается как ошибка.
Поэтому отсутствие ошибок и одинаковые логины сами по себе не доказывают,
что обработчик дошёл до конкретного run. Полная причина текущего отказа на
производственном сервере без данных о целях/источниках не установлена.

Доработка даёт отдельный проверяемый путь подтверждения уже существующей
блокировки. Это не принудительное изменение статуса и не запуск блокировки.

## Поведение

- На странице сопоставления при наличии сохранённых связей появилась кнопка
  «Проверить завершение». При новом подтверждении/сохранении сопоставления
  такая же проверка выполняется автоматически.
- Требуются роль admin и CSRF, открытая существующая задача с диагностикой
  ad:conflict и аудит явного подтверждения её AD-идентичности.
- Из текущих сопоставлений должен определяться один непустой objectGUID без
  противоречий. Чужое сопоставление GUID запрещает действие.
- AD читается строго по этому GUID, без перехода на похожий/сгенерированный
  логин. Проверяются совпадение GUID, ФИО и явно подтверждённое is_enabled=False.
- Отсутствующая, активная, недоступная или неопределённая учётка не приводит
  к успеху. Активную AD этот путь не блокирует и не восстанавливает.
- До и после LDAP-чтения повторяются проверки: нет активной занятости в любой
  организации, нет выполняющегося импорта, не изменился эпизод увольнения,
  наступил срок с учётом отсрочки, не сменилось сопоставление/владелец GUID.
- В день увольнения до окна блокировки действие не завершается. Просроченную
  задачу можно подтвердить днём. Не нужно ждать сегодняшнего вечернего экспорта
  для этого чтения: никаких внешних команд изменения доступа не выполняется.
- Прежний планировщик снимает только устранённую диагностику, текущая цель
  фиксируется already_completed/already_disabled, и результат пересчитывается
  штатным способом. Прочие реальные ошибки/цели не скрываются. Отмечается
  отдельный аудит `dismissal_ad_completion_verified` с mode=read_only.
- Если все цели этой AD-задачи подтверждены, она немедленно становится success,
  исчезает из ближайших и появляется в журнале. Это не утверждение, что все
  независимые организационные действия Zimbra/DSM/Техэксперта завершены.
- Штатный фон, вечерние защиты внешних команд, политика увольнений по организациям
  и автоматическое восстановление не менялись. Вызовы _process_ad/_process_target,
  disable/enable/delete/create, команды Zimbra здесь не используются.

Сохранённое сопоставление остаётся сохранённым, даже если последующая проверка
откажет. На странице показано сообщение проверки; таблица сопоставлений обновляется.

## Для текущего случая

После установки и пересборки контейнера войти администратором и открыть путь
на вашем сервере `/dismissals/101/ad-mapping`. Нажать «Проверить завершение».
Вводить kotlyarenko.av и сохранять обе связи повторно не требуется.
При подтверждении отключённой AD запись должна уйти в журнал сразу.
Если проверка откажет, нужен точный текст показанной причины, а не ожидание
ещё нескольких часов. Производственная AD и БД из среды разработки не изменялись.

## Проверки и установка

92 профильных pytest, включая 18 новых: чтение без вечернего gate, активная AD
без блокировки, отсутствие/другой GUID/ФИО/неизвестный статус/недоступность AD,
отсрочка, время окна, просроченная задача, изменения HR/импорта/сопоставления
во время LDAP, чужой GUID, сохранение других ошибок, действие веб-формы и CSRF.
Мутирующие методы AD не вызывались; в тестах AD подменена.
Проверены py_compile, Jinja-рендер и вид страницы в браузере с новой кнопкой.
JavaScript не менялся. Новый тест использует fixture из существующих
test_dismissal_ad_mapping/test_ad_conflict_recovery указанного HEAD.

Архив содержит 3 изменённых и 2 новых файла, repo-relative пути. Удалений нет.
Новых зависимостей и изменений схемы БД нет. Перед установкой сохранить копию
исходников и резервную копию БД. Распаковать поверх проекта, пересобрать
существующий Docker-сервис и пересоздать контейнер с теми же настройками,
compose-проектом и томами. Не удалять БД/тома. Одного restart недостаточно.
Автоматическое развёртывание не выполнялось. ZIP integrity и SHA-256 проверены.
